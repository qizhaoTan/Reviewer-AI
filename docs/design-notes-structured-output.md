## 一、行号：不让模型报，用 anchor 反推

### 问题

原设计的 `Finding` 有 `Line int` 字段，由模型填写。这是错的。

模型看到的是 unified diff，行号信息藏在 `@@ -12,7 +12,9 @@` 这类 hunk header 里。要得出"某一行在新文件里是第几行"，模型必须从 hunk 起点开始逐行累加上下文行和新增行、同时跳过删除行——这是纯计数任务，正是大语言模型最不可靠的地方。

更糟的是**错了没人发现**：一个偏了 3 行的行号看起来完全正常，直到用户点开发现指的是别的代码。

### 决策

模型只提供 `Anchor`——它正在评论的那段代码的**逐字引用**（可多行）。行号由确定性算法把 anchor 贴回 diff 算出，填进 `StartLine`/`EndLine`。

```go
type Finding struct {
    Anchor    string // 模型填：逐字复制的代码片段
    StartLine int    // 算法填，不接受模型提供
    EndLine   int
}
```

分工原则：**模型做它擅长的（复制它正在看的内容），算法做模型做不好的（数行号）。**

`NormalizeReport` 会主动丢弃模型硬塞进来的 `StartLine`/`EndLine`，否则就退回了"相信模型数行号"这个本来要解决的问题（有对应测试固定这条）。

### 实现要点（`internal/review/anchor.go`）

参考了 `~/work/github/open-code-review/internal/diff/resolver.go`，其中两条是实战经验，凭空设计想不到：

1. **归一化时要剥掉行首的 `+`/`-` 标记**。模型经常直接从 diff 里连着 `+` 号一起复制代码，不剥的话这类 anchor 一律匹配失败。
2. **归一化时丢弃空行**，所以"连续"指的是相邻的**非空行**。模型复制代码时容易多带或吞掉空行，对空行敏感会白白丢掉大量本该匹配上的 anchor。

另外：忽略缩进差异（`TrimSpace`），让匹配对空格/tab 不敏感。

### 匹配策略的三个取舍

| 情况 | 决策 | 理由 |
|---|---|---|
| anchor 匹配到多处 | 取第一处，不报错 | anchor 是多行片段，多行连续完全相同概率很低；真撞上了，给第一处也比没有行号强 |
| anchor 匹配不到 | **不算错误**，退化为文件级意见（行号留 0） | 一条意见的价值在它指出的问题，不在坐标。因为定位不到就丢掉整条意见是本末倒置 |
| 意见针对被删除的代码 | 先在新文件侧找，找不到退到旧文件侧 | "这段不该删"这类意见只能在旧侧找到，返回旧文件行号聊胜于无 |

### 刻意不做

参考实现在 hunk 匹配失败后会 fallback 去扫完整的新文件内容。我们的 `gitdiff.Change` 只有 `Patch` 没有全文，要加就得引入文件 IO 和错误处理。hunk 匹配已覆盖绝大多数情况（anchor 本就该指向改动处），先不做。

## 二、submit_review 的结果怎么交给 engine

这是本阶段讨论最久的问题，中间推翻过三次方案。

### 问题的本质

`ITool.Execute` 的签名固定返回 `Result{Output, IsError}`，没有地方放结构化的 `Report`。而 `Output` 的职责是"**回喂给模型看的文本**"——把 JSON 序列化进去，等于让一个面向模型的字段兼任程序间的数据总线，两种职责混在一起。

排除 `Output` 之后，输出的目的地只有三种可能的载体：**参数、context、返回值**。

### 候选方案对比

| 方案 | 载体 | 工具能否单例 | 依赖可见性 | 主要代价 |
|---|---|---|---|---|
| 工具持 `Out *Report` 指针 | 结构体字段 | ❌ 有状态 | 编译期 | 每条审查链路必须 new 一个实例 |
| context 传 sink | 参数 | ✅ | **运行期** | 取不到时只能返工具错误，问题伪装成"模型提交失败" |
| `Result.Payload any` | 返回值 | ✅ | 编译期（弱） | 类型不具体，需要类型断言，污染公共契约 |
| **`Result.ReviewResult *review.Report`** | 返回值 | ✅ | 编译期 | 公共 `Result` 多一个只服务单个工具的字段 |

### 决策：`Result` 加具名字段

```go
type Result struct {
    Output       string
    IsError      bool
    ReviewResult *review.Report // 只有 submit_review 填，其余工具留 nil
}
```

**为什么排除 context**：`context.WithValue` 的定位是取消信号、超时、跨 API 边界的请求域元数据，不是业务输入（其文档明确写着"不要用它传递函数的可选参数"）。更实际的代价是——取不到值时编译器不报错，只能在运行时返回一个工具错误，而这个错误会伪装成"模型提交失败"回喂给模型，模型会**反复重试**（它以为是自己参数错了），烧掉几轮调用才暴露出真正的原因是 engine 忘了塞值。在一个每轮都花钱的流程里，这个代价被放大。

**为什么用具名字段而不是 `Payload any`**：类型具体、编译器可查、调用方不需要类型断言、读代码的人一眼看得出装什么。

**代价是可见且有界的**：一个具名字段 + 一行注释说清谁填谁不填，并有测试固定"其他工具必须留 nil"这条约定（误填会让 engine 把普通工具调用误判为"审查已提交"而提前终止循环）。

**额外收获**：engine 靠 `result.ReviewResult != nil` 就能判断审查是否已提交，**不需要按工具名做字符串比较**，少一处硬编码。

## 三、一次完整审查 = 一个 Run

主 Agent、子 Agent、复核 Agent 跑完全部流程，统称为**一次完整审查**，对应**一条 `store.Run` 记录**。所有中间状态都在这条记录上，随时可恢复。

由此推出一条**比原计划更早的落盘时机**：初审 Report 一提交就应立即落盘，不等复核完成。因为复核是 N 条 finding × 每条一个 tool loop 的重活，跑到一半崩了却没存初审结果，恢复时就得让模型重审一遍，白白浪费已完成的初审。

这也决定了 `Critiqued` 字段的归属：它属于 `store.Run`（表达"初审已完成、复核未完成"这个中间状态），不属于工具层。恢复逻辑随之清晰——命中 `in_progress` 的记录时，若 `Findings` 非空但 `Critiqued=false`，跳过主循环直接进复核阶段。

## 四、职责边界：工具产出结果，engine 负责落盘

### 被否决的方案：把 `Run` 传给工具，让工具直接操作

看起来很自然（"所有 Agent 的结果都该体现在 Run 上"），但有两个问题：

**1. 加锁解决不了整体覆盖的丢更新。**
`SaveRun` 是整条记录覆盖写。锁能保证单次读-改-写不被打断，但 A 和 B 各自"读 Run → 改自己那部分 → 整体写回"时，除非把**读到写的全过程**都锁住（等于把并发串行化），否则后写的会覆盖先写的。这不是数据竞争，是语义问题，`-race` 也测不出来。

**2. 包依赖会绕起来。**
`tool` 目前不碰持久化，所以 `Execute` 的测试不需要数据库。让它导入 `store`，而 `store` 又要导入 `review` 存 `Findings`，依赖网就乱了。

### 采纳的分工

> **工具负责"产出结果"，engine 负责"把结果放进 Run 并落盘"。**

锁的问题和依赖问题一起消失，工具保持可独立测试。

## 五、工具形态：无状态、单实例、共享

### `SubmitReviewTool` 是无状态的

结果走返回值而非实例字段，因此一个实例可以被本次审查里的**所有 Agent**（主 Agent、阶段五的并发子 Agent）共享，不会互相覆盖，也不需要锁。有并发测试固定这条性质。

### `Changes` 用全量，且全局共享

```go
type SubmitReviewTool struct {
    Changes []gitdiff.Change // 全量快照，本次审查内固定不变、只读
}
```

三个理由：本次审查范围内**固定不变**、**不提供给模型**（只用于校验 file 归属和 anchor 定位）、**只读**。既然只读且不变，共享就是安全的。

**这里推翻过一次错误判断**：曾认为"子 Agent 的 Changes 各不相同"，实则混淆了两件事——

- 子 Agent 的 **prompt** 里只放它负责那部分文件的 diff（这是分组的意义）
- `submit_review` 用来**校验 file 合法性**的 `Changes`，是**全量**的

这两者本就不该是同一份数据。用全量校验反而更合理：子 Agent A 在审 `db.go` 时发现问题根源落在 B 负责的 `api.go` 上，全量校验才不会误拒这条有效意见。

### 为什么 `Changes` 不走 context

同"二"中排除 context 的理由。补充一点：把 `Changes` 挪进 ctx **换不到任何东西**——工具已经可以单例共享了（之前需要 per-链路 new 实例的是 `Out` 指针，那个已经删掉）。付出运行期失败的代价却没有收益。

`SubmitReviewTool` 有字段而 `ReadFileTool{}`/`GlobTool{}` 是空结构体，这个不对称是真实的，但有正当理由：后三者的输入完全来自模型的 `args` 加 `Execute` 的 `repoRoot`；而 `submit_review` 需要一份**模型不提供、也不该提供**的数据（本次改动范围），只能由程序侧注入。

若要彻底消除这个不对称，正统做法是给 `Execute` 加参数而非塞 ctx——但那要改所有工具的签名，只为一个工具服务，代价明显更大。

### 被删掉的 `Collector`

曾引入过一个带互斥锁的 `review.Collector` 承载提交结果。改用返回值后它失去了存在理由：

- 它的生命周期不超过一次 tool loop，右边所有环节（复核、落盘、Web、reply、增量重审）打交道的都是 `store` 里的持久化数据，**没有任何实体需要访问它**
- 剥掉 `rejected`（只被测试读，真要观测应该由 engine 打日志）和 `Critiqued`（归属 `store.Run`）之后，它只剩一个 `Report`，等价于一个指针

## 六、复核（Critique）的参数

| 项 | 决策 |
|---|---|
| 触发时机 | 每次审查后无条件跑 |
| 使用的模型 | 复用初审的同一个 provider（不引入独立的 critic 角色配置） |
| 复核者可见的上下文 | 该条 Finding + 它所在文件的 diff + `read_file`/`glob`/`grep` 只读工具（可自行查证代码） |
| 复核的输出 | 保留/丢弃二元判定 + 理由（只做减法，不新增 Finding） |
| 并发与轮数上限 | 可配置，默认并发 10、每条最多 30 轮 |
| 被丢弃的 Finding | **落盘保留**（带 `Kept=false` 和 `CritiqueReason`），只是不展示 |

保留被丢弃项的理由：阶段三 Web 可视化时能看到"复核干掉了什么、为什么"，这对调优提示词很有价值，也是手工验证复核是否真的起作用的唯一依据。

因为复核者能调用只读工具，每条 finding 的复核是一个完整的 tool loop 而非单次 `Generate`——模型调用量会比初审高一个数量级。这是明确接受的成本。

## 七、其他约定

**`Finding.ID` 一律由程序重新分配**（`f1`/`f2`/…），不信任模型填的值。模型在一次提交里给出重复 ID 是常见现象，而 ID 是阶段四 reply/withdraw 的锚点——ID 撞了，用户回复第二条意见就会撤回第一条。

**`Severity` 只有三档**（`info`/`warning`/`error`）。档位再多模型的判断会飘忽，人也说不清 "major" 和 "critical" 的界线。排序权重用 map 而非字符串比较——`"error" < "info" < "warning"` 的字典序跟严重程度完全相反。JSON Schema 的 enum 从 `review.AllSeverities()` 派生，避免"告诉模型有四档、校验时按三档拒绝"的不一致。

**`submit_review` 校验 `file` 必须在本次改动范围内**。拦的是"模型评论了一个只是顺路读过、但本次没改的文件"——超出审查范围，且文件不在快照里也没有 patch 供 anchor 定位。错误信息会列出可选的文件名。

**空 findings 是合法的、且必须带 summary**。"确认无问题"和"模型跑飞了"必须能区分开，所以即使没有发现问题也要求模型显式调用 `submit_review` 并解释为什么这次改动看起来没问题。

**工具的错误信息必须同时说明"错在哪"和"该怎么改"**（沿用项目既有约定）。这些文字会回喂给模型用于自我纠正，含糊的错误信息会多耗一轮调用。测试断言的是错误里**包含具体片段**，不只是"有错误"——错误信息的质量本身就是功能。
